# CourseRaptor 用户体验审计报告

**审计日期**：2026-08-28
**审计视角**：产品经理
**证据来源**：`session.json`（10 轮真实对话）、`memory.json`（11 条长期记忆）、`qq-bridge.log`、`src/` 全量代码走查

---

## 一、审计方法

不看 README 的宣传口径，只看两件事：

1. **用户实际怎么问** —— `session.json` 里 10 轮 user 消息是唯一真实行为样本
2. **产品实际怎么兜** —— 工具层能不能直接覆盖，还是靠模型临场发挥

判断标准很简单：**能力长在工具里 = 产品保障；能力长在模型脑子里 = 碰运气。**

### 提问意图分布（10 轮）

| 意图 | 轮次 | 能力归属 |
|---|---|---|
| 通知 · 列表 | 3 | 有工具，但信噪比低 |
| 课表 · 全学期 | 2 | `get_schedule` 直接覆盖 |
| 课表 · 第 N 周 | 2 | **无工具，模型现算** |
| 通知 · 待办筛选 | 1 | **无工具，模型发挥** |
| 学籍信息 | 1 | `get_student_info` 直接覆盖 |
| 术语解释 | 1 | **无工具，靠模型知识** |

**结论：10 轮里只有 3 轮是开箱即用的。**

## 二、P0 · 结构性硬伤（建议本周修）

### P0-1　QQ 渠道长任务必然超时

**现象**：用户在 QQ 里发「开抢」，大概率永远收不到结果。

**证据链**：

| 位置 | 事实 |
|---|---|
| `src/qq/bridge.ts:126` | `await agent.generate(...)` —— 同步阻塞，任务跑完才发消息 |
| `src/tools/index.ts:579` | `grab_plan` 的 `durationSec` 默认 **600 秒** |
| `README.md:103` | 「官方机器人为被动回复（约 5 分钟窗口）」 |

600 秒的任务，在第 300 秒之后发出的任何回复都已超出被动回复窗口。**任务跑得越久，用户越收不到。**

**用户感受**：发出指令 → 10 分钟死寂 → 什么都没有。既不知道在跑，也不知道跑完了没。

**建议**：三选一，按性价比排序

1. **QQ 渠道专属时长上限**（最快）：`createRaptorAgent("qq")` 时把抢课类工具的 `durationSec` 上限压到 240 秒，并在工具描述里写明。
2. **先应答后执行**（体验最好）：收到指令立即回一条「已开始盯课，约 X 分钟后回报」，任务转后台，完成后用主动消息推送。
3. **进度心跳**：长任务期间分段推送（如每 60 秒报一次余量变化），顺带解决「黑盒等待」问题。

> 附带收益：方案 2、3 同时解决终端侧的等待焦虑——成绩查询 ~10 秒、抢课 600 秒，目前全程无任何进度反馈。

---

### P0-2　欢迎语与用户明确偏好自相矛盾

**现象**：QQ 激活欢迎语主动提到了用户明令禁止提及的功能。

**证据链**：

| 位置 | 内容 |
|---|---|
| `memory.json` · `mmt8dv2mqwbuu` | 「对外展示时不要提及抢课和盯课功能」 |
| `memory.json` · `mmt8duq46b4ff` | 同上，措辞略异的**重复条目** |
| `src/qq/bridge.ts:108` | 写死：`"查课表 / 盯课 / 抢课 / 读教务通知"` |

用户把偏好郑重存进了长期记忆，代码里的文案却反着来。这是**已经在线上生效的自相矛盾**。

**建议**：

- 欢迎语改为：`"已授权，迅猛龙上线！直接说需求即可：查课表 / 查成绩 / 读教务通知。"`
- 欢迎语文案抽到配置常量，避免散落在代码里再次漂移。

---

### P0-3　错误文案直接甩技术黑话

**现象**：出错时用户看到的是 `❌ 处理失败：SESSION_EXPIRED`。

**证据**：`src/qq/bridge.ts:143`

```ts
await bot.sendText(msg.replyTarget, `❌ 处理失败：${(e as Error).message.slice(0, 120)}`);
```

**用户感受**：不知道这是「重试就好」还是「彻底坏了」，也不知道该等多久。

**建议**：错误分级 + 人话转译 + 明确下一步

| 底层错误 | 给用户看 |
|---|---|
| `SESSION_EXPIRED` | 「登录态掉了，我正在重新登录，稍等几秒再问一次就好」 |
| 网络类 | 「教务系统这会儿连不上，多半是线路抖动，稍后再试」 |
| 解析类 | 「页面结构可能变了，这个查询暂时不可用」 |

至少要做到：**不说用户看不懂的词，且每次都给出下一步动作。**

## 三、P1 · 高频需求缺口（建议两周内）

### P1-1　「第 N 周的课」没有工具支撑

**这是本次审计最有价值的发现。**

**证据**：10 轮对话里课表提问 4 次，其中 **2 次是「第一周」**：

- `#16`「第一周的课」
- `#26`「我第一周的课表」

而 `get_schedule` 的入参只有 `semester`，**没有 week**（`src/tools/index.ts:599-604`）。

于是模型每次都要：读全学期课表 → 解析 `weeks` 字段里的 `"2-6,8-12"`、`"1-12,14-17"` 这类表达式 → 自己判断哪些课落在第一周 → 组织输出。

**问题不在于模型算不对，而在于**：

1. 这是**可复现的高频需求**，不该每次都烧 token 重算
2. 周次表达式解析是**有出错空间的机械劳动**，交给模型就是把可靠性押在概率上
3. 用户问了两遍，说明这个需求会反复出现

**建议**：

- `get_schedule` 增加可选 `week` 参数，在工具层完成周次过滤
- **顺手补上「今天的课」** —— 课表类 agent 的最高频场景。目前要模型自己完成三步推理（今天周几 → 当前第几周 → 过滤周次），任一步出错答案就错了

> 这两条做完，课表场景的能力归属就从「红」变「绿」，覆盖了真实提问的 40%。

---

### P1-2　通知列表信噪比太低

**证据**：3 次通知提问，用户第 2 轮就追问「有哪些是我需要注意的」。

`get_news` 返回 10-30 条平铺列表，用户得自己从《2026年申报增设本科专业的公示》里判断跟自己有没有关系。

**值得肯定**：agent 在 `#11` 那条回复里做得很好——按时间排序、用 🔴🟡🟢 分优先级、落到具体日期和地点。**但那是模型的临场发挥，不是产品保障。** 换个模型、换个上下文，可能就没了。

**建议**：把这次的优秀表现固化下来

- `get_news` 返回时带 `relevance` 标记：用 `memory.json` 里已有的年级/专业/班级做关键词匹配（用户档案已存在，数据是现成的）
- 或新增「待办摘要」能力：把相关通知转成「什么时候 / 做什么 / 在哪 / 不做会怎样」的行动清单

---

### P1-3　长期记忆没有治理机制

**证据**：`memory.json` 11 条中

| 问题 | 实例 |
|---|---|
| **重复条目** | `mmt8dv2mqwbuu` 与 `mmt8duq46b4ff` 内容近乎完全一致 |
| **过期条目占位** | 「抢课计划（2026-08-27 执行）」已完成，仍永久注入上下文 |
| **无上限** | 每次启动全量注入，只增不减 |

**后果**：上下文持续膨胀 → 成本上升、模型注意力被稀释、陈旧信息可能覆盖新结论。

**建议**：

- `add` 前做相似度去重（现有两条重复就是没去重的直接证据）
- 条目支持 `expiresAt` / `status`（如任务类完成后自动归档）
- 注入时过滤已过期条目，只保留有效记忆

## 四、P2 · 打磨项（有余力再做）

### P2-1　冷启动零引导

终端启动后是一个空对话框。README 里那段精彩的示例对话（课表/通识选修/通知/记忆）用户**在终端里根本看不到**。

**建议**：首屏展示 3-4 个可点击的示例 prompt，把 README 的价值搬进产品。

### P2-2　教务术语门槛

用户问了「注册是什么意思」。教务黑话一堆：注册/报到/正选/补退选/通识选修六类/教学班/节次。大一新生尤其看不懂。

**建议**：系统提示词加一条规则——解释教务术语时，先给一句白话定义，再给操作细节。

### P2-3　短期记忆全量注入

`src/memory/shortterm.ts:17` 的 `MAX_TRANSCRIPT_CHARS = 3000`，把上次会话整段塞进提示词，包含早已解决的事。

**建议**：注入前做摘要，或只取最后 N 轮。

## 五、值得保留的设计

审计不该只挑毛病，这几个设计是明显的产品品味，建议在后续迭代中保住并推广：

1. **`src/jwgl/term-dates.ts` 的 `recorded / known / estimated` 三态**
   开学日期查不到时宁可标注「估算」也不装作确定，还会主动提示「把报到注册通知链接发我可校准」。这是**不骗用户**的产品价值观，应该推广到所有不确定数据上。

2. **工具层对「拿不到 ≠ 没有」的严格区分**
   课表查询失败时会明确说「这与课表为空不是一回事」。避免用户被误导。

3. **敏感字段自动打码**
   学籍信息中的证件号/银行卡号只留前 4 后 4，避免完整 PII 进入模型上下文。

4. **抢课工具默认关闭**
   `RAPTOR_ENABLE_GRAB` 开关让真实操作类能力在平时隐藏，是对用户的保护。

| 优先级 | 事项 | 预期收益 | 工作量 |
